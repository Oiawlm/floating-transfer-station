## 2. 社区惯例总结

### 2.1 图片通常放哪个目录

- `docs/`（及其子目录 `docs/images/`、`docs/screenshots/`、`docs/assets/`）：**最常见之一**。好处是与 GitHub Pages 文档站共用同一份资产，README 与站点引用同一路径。
- `assets/`：用途明确、语义干净的独立媒体目录，常见于不想污染 `docs/` 的项目。
- `.github/` 与 `.github/assets/`：把「只服务 README / Issue 模板」的图放在这里，根目录最干净，是近年较受推荐的做法。
- `media/`、`images/`、`screenshots/`、`resources/`、`static/`：语义化变体，均存在。
- 仓库根目录直接放图：**反模式**，会与代码文件混在一起。

命名惯例（经验值）：全小写 + 连字符，语义化如 `demo-search.gif`、`hero-light.png`、`screenshot-dark.png`；避免 `1.png`、`image (1).png`。

引用方式：优先**仓库内相对路径**（`docs/demo.gif`），而非 `raw.githubusercontent.com` 绝对 URL——相对路径在分支改名/仓库迁移时更稳，且不会绕过 CDN 缓存策略。（两种做法社区都在用，**该偏好为经验判断，需核实是否有官方立场**）

大体积媒体的处理：部分项目用 **Git LFS** 追踪 `*.gif` / `*.mp4`，或用 `.gitattributes` 控制（哪些项目这么做 **需核实**）。GitHub 仓库文件的官方阈值常识：单文件 > 50 MB 会警告、> 100 MB 会被拒绝；Web 渲染体验建议图片单文件保持在 **5 MB 以下**（**该 5 MB 为经验建议，需核实是否写入官方文档**）。

### 2.2 Hero GIF / 主截图放置位置

- 典型顺序：`# 项目名` → 徽章行 → **hero 视觉** → 一句话简介 → 安装/使用。
- 少数项目把 hero 放在标题与徽章之间（视觉冲击优先），或紧贴标题下方。
- 居中排版通常用 HTML：`<p align="center"><img src="docs/hero.gif" alt="..." width="720"></p>`（Markdown 原生 `![]()` 无法居中、也无法控宽）。
- 多图并排：用 `<p align="center">` 或多个 `<img>`，或用 HTML `<table>`；避免多张大图纵向堆叠把「安装命令」推到首屏之外。
- 次要演示（高级功能、插件）常折叠进 `<details><summary>更多截图</summary>...</details>`，以降低首屏加载成本。

### 2.3 体积 / 时长 / 分辨率经验值（社区经验，非规范）

- **GIF 体积**：常见落在 1–5 MB；≤ 2–3 MB 为佳；> 10 MB 普遍被视为过大（移动端与弱网首屏会很痛）。
- **时长**：5–15 s 循环最舒服；超过 30 s 的动图基本没人看完。理想是「3–8 s 讲清一个动作」。
- **帧率**：GIF 常见 10–15 fps；动作交互 15 fps 已足够，过高会线性放大体积。
- **宽度**：600–1200 px 是甜点区；整窗截图常用 800–1000 px 级。配 High-DPI 时导出 2× 资源，再用 `<img width="...">` 显示为逻辑尺寸。
- **静态截图**：PNG 单张建议 < 200–500 KB；纯 UI 截图用 PNG（文字锐利），照片类才考虑 JPEG/WebP。
- **调色板陷阱**：GIF 仅 256 色，UI 里的渐变、阴影、抗锯齿边缘容易出现色带/噪点。用 **gifski**、**gifsicle -O3** 等做有损优化 + 抖动控制。
- **GitHub 上传上限**（常识，**需核实具体当前值**）：Issue/PR/评论中的图片附件有体积上限（常被引为 10 MB 级），超出需走仓库文件或图床。

### 2.4 GIF vs 静态图 vs 视频的取舍

- **静态图**：UI 布局、主题展示、结果状态——能静则不 G。
- **GIF**：只有「动作/交互/时序」本身是信息时才用（呼出面板、拖拽、实时预览、动画过渡）。
- **视频（MP4/WebM）**：体积效率远高于 GIF。可用 `<video autoplay loop muted playsinline width="720" src="...">` 内嵌；GitHub 支持把 mp4 以附件形式上传并在 Markdown 中渲染为播放器（**渲染行为与自动播放策略需核实**）。
- 权衡：GIF 兼容性最好（各客户端、Markdown 预览、镜像站都能显示），视频更省流量但可能不自动播放、部分渲染环境不支持。**大多数项目仍以 GIF 作为 README 主视觉，视频用于文档站或 Release 说明。**

### 2.5 alt 文本写法

- 描述**动作与结果**，而不是「一张图片」：`![演示：按下 Ctrl+Space 呼出启动器，输入 firefox 后回车打开浏览器](docs/demo.gif)`。
- 保留关键快捷键、菜单名、文件名等可检索关键词——alt 也是 SEO 与可访问性的一部分。
- 不为装饰性 banner 写长 alt，写短语义或 `alt=""`（纯装饰）。
- GIF 无法向屏幕阅读器传达运动信息，alt 要承担「用文字复述这段动图」的职责。

### 2.6 深浅色主题如何展示

- 现代做法：用 `<picture>` + `prefers-color-scheme` 媒体查询，GitHub 渲染 README 时通常会遵循系统主题（**该能力需核实当前支持范围**）。
  `<picture><source media="(prefers-color-scheme: dark)" srcset="docs/hero-dark.png"><img src="docs/hero-light.png" alt="..." width="720"></picture>`
- 维护两套资产的成本高，因此更常见的折中是：**只出一套中性背景截图**（或用窗口自带投影的透明 PNG，适配任意底色）。
- 另一种：一张图里并排展示 Light / Dark 两种主题（节省一次滚动，也直观传达主题能力）。
- GIF 的双主题版几乎没人做（成本翻倍）——结论：**动图通常只出一版，主题展示交给静态图。**

## 3. 常见反模式

1. **GIF 过大（> 10 MB）**：首屏加载缓慢，移动端/弱网几乎不可用，也拖慢镜像与第三方文档站。
2. **全屏不裁剪**：录了整个 4K 桌面，真正变化的区域只占 5%，观众要费力找重点。应裁剪到窗口、必要时局部放大。
3. **降采样不当**：高分辨率录屏直接缩成小 GIF，导致文字糊成一团、色带明显，反而比静态图更差。
4. **信息密度过低**：动图前 3 秒在等待、鼠标乱晃、窗口缓慢打开；真正有效信息只有最后一瞬。应剪掉一切等待与过渡。
5. **时长过长 / 循环点不清**：> 30 s 或结尾不回环，观众不知道何时该看哪里。
6. **鼠标轨迹不可见或过快**：要么光标被裁掉，要么速度超快让人跟不上操作；反之拖沓亦然。
7. **动图代替静态图**：本来一个静态界面截图就够，却用 GIF 造成无谓体积。
8. **缺少 alt 文本**：不仅无障碍不达标，也让纯文本/被墙渲染环境下 README 变成空白。
9. **用 GIF 承载声音信息**：GIF 无声，需要音频的教学演示应改用视频。
10. **首屏堆叠多张大图/GIF**：把安装说明、徽章、核心卖点全推到折叠线下。
11. **图片散落根目录**：仓库根被 `1.png`、`gif2.gif` 污染，无目录约定。
12. **相对路径大小写不匹配**：Windows/local 不敏感、Linux/GitHub 敏感，图挂了才发现（`Docs/Hero.PNG` vs `docs/hero.png`）。
13. **不展示终态**：动图停在操作中，没给出「结果长什么样」，说服力大打折扣。
14. **跨项目尺寸不一致**：同一 README 里多张图宽度/风格不一，观感廉价。
15. **装饰性 banner 喧宾夺主**：占满一屏却零信息量，读者必须先滚过它才能看到项目是干什么的。

## 4. 附：社区常用制作与优化工具（供参考）

- 录制：ScreenToGif（Windows，开源）、LICEcap、Kap（macOS）、Peek（Linux）、asciinema / Terminalizer / charmbracelet/vhs（终端场景）。
- 压缩优化：gifski、gifsicle、ffmpeg（gif→mp4/webm 的转换与调色板生成）。
- 惯例：先按目标宽度录制 → 裁剪到窗口 → 降帧到 10–15 fps → 优化调色板 → 目标 ≤ 3 MB 再入库。
