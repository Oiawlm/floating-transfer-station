# Ctrl+P 批量置顶安全边界设计

## 用户结果

用户在面板收起或正在编辑分类名称时按 `Ctrl+P`，不会静默改变此前保留但当前不可见的卡片选择。只有当前分类面板展开、焦点不在文字编辑器、窗口未关闭且存在可操作选择时，`Ctrl+P` 才能执行批量置顶或取消置顶。

## 根因与方案选择

当前 `BatchPinCommand_CanExecute` 只检查选择、关闭状态和保存状态；`ApplyBatchPinSelectionAsync` 也没有检查面板展开与文字焦点。面板收起后 `BoardList.SelectedItems` 按既有设计继续保留，因此路由命令仍会把隐藏选择视为可操作范围。分类名称编辑框获得焦点时也会把 `Ctrl+P` 路由到窗口命令。

采用在命令查询和实际执行入口共同补齐上下文守卫的方案。`CanExecute` 负责让正常 WPF 路由不触发命令；`ApplyBatchPinSelectionAsync` 再验证同一关键状态，防止查询与执行之间状态变化，按钮入口继续复用同一业务路径。

不采用“面板收起时清空选择”，因为这会改变已经由 `Esc`、删除快捷键和异步置顶回归锁定的选择保留语义。也不改用新的全局按键处理器，因为现有 `RoutedUICommand` 已负责 `Ctrl+P` 手势，新入口会重复路由并增加与 `TextBox` 竞争的风险。

## 行为边界

- 面板收起时，保留的选择保持不变；`Ctrl+P` 不可执行、不写入磁盘、不改变置顶状态。
- 分类名称编辑器拥有键盘焦点时，窗口不接管 `Ctrl+P`；选择、分类草稿和置顶状态保持不变。
- 当前面板展开、焦点不在文字编辑器、窗口未关闭、没有批量置顶正在保存且选择非空时，原有批量置顶或取消置顶行为保持不变。
- 标题栏批量置顶按钮继续调用同一执行入口；正常可见点击不受影响。
- 不改变持久化格式、原子保存与失败回滚、置顶分区、批量顺序、拖放载荷、分类名称保存或安全卸载边界。

## 数据流与失败处理

WPF 查询 `BatchPinCommand` 时先让文字编辑器保留命令路由，再检查窗口、面板、选择和保存状态。命令真正进入 `ApplyBatchPinSelectionAsync` 后重新检查关闭、面板展开、文字焦点、保存状态和活动分类；任一条件不满足就直接返回，且不捕获选择、不调用 `BoardMutationService.SetPinnedAsync`。合法路径继续按活动分类显示顺序冻结选择、一次保存，并沿用现有失败恢复、选择版本和滚动位置逻辑。

## 验证

真实 STA WPF 回归分别覆盖折叠后保留选择、分类名称编辑器焦点和正常展开命令：前两种场景必须 `CanExecute == false`、保存次数为零、选择与置顶状态不变；正常场景继续单次保存并改变所选卡片。另用两个数据行直接调用执行入口，证明即使绕过命令查询，折叠态与文字焦点仍会被拒绝。生命周期测试锁定 README 与 CHANGELOG 的公开边界说明。
